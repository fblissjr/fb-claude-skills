# MCP spec 2026-07-28: what it breaks, and where this repo stands

Filed 2026-08-07 when the owner asked to "source and update mcp to the latest
spec". The answer to the second half is that **it is a migration, not a bump**,
so this records the gap rather than papering over it.

**Status: nothing migrated.** One footgun closed (below); the migration itself
is unscoped and unstarted.

## Where this repo actually stands

| Unit | SDK pinned | SDK installed | Spec it implements |
|---|---|---|---|
| `apps/readwise-reader` (MCP server) | was `mcp[cli]>=1.26.0`, now `==1.28.1` | `mcp` 1.28.1 | pre-2026-07-28 |
| `apps/skill-dashboard/mcp-app` | `@modelcontextprotocol/sdk ^1.24.0` | 1.27.1 | pre-2026-07-28 |
| | `@modelcontextprotocol/ext-apps ^1.0.0` | 1.2.2 | — |

The current Python SDK is **2.0.0**, whose `LATEST_PROTOCOL_VERSION` is
`2026-07-28`. Note its `DEFAULT_NEGOTIATED_VERSION` is still `2025-03-26`, so
"the SDK supports the new spec" and "your server speaks it" are different
claims.

Derive the first two columns with `grep mcp apps/*/pyproject.toml
apps/*/mcp-app/package.json`; the third by reading
`coderef/mcp/modelcontextprotocol/docs/specification/2026-07-28/changelog.mdx`.

## The footgun that was live

`readwise-reader` is an application and floor-pinned `mcp[cli]>=1.26.0`. Since
`mcp` 2.0.0 is published, **any re-lock would have crossed a major boundary
silently** and pulled an SDK implementing a stateless protocol under code
written for a stateful one. The repo's own convention already says applications
pin exact; this one did not. Now `==1.28.1`, matching what its lock already
resolved.

`skill-dashboard` is the milder version of the same: `^1.24.0` on an
application, where the convention says exact. A caret cannot reach 2.x, so it is
a convention drift rather than a hazard. Left alone pending the same decision.

## Why 2026-07-28 is a migration

From the spec's own changelog. These are not additive:

1. **Protocol-level sessions removed** from Streamable HTTP, along with the
   `Mcp-Session-Id` header. Cross-call state becomes explicit server-minted
   handles passed as ordinary tool arguments.
2. **MCP is stateless**: the `initialize` / `notifications/initialized`
   handshake is gone. Every request carries its protocol version and client
   capabilities in `_meta`.
3. **`server/discover` is mandatory** — servers MUST implement it to advertise
   supported versions, capabilities, and identity.
4. **`subscriptions/listen` replaces** the HTTP GET endpoint and
   `resources/subscribe` / `resources/unsubscribe`.
5. **`ping`, `logging/setLevel`, and `notifications/roots/list_changed` are
   removed.** Log level moves to a per-request `_meta` field.
6. **Tasks leave the core protocol** for an `io.modelcontextprotocol/tasks`
   extension, with polling via `tasks/get` replacing blocking `tasks/result`.
7. **MRTR replaces server-initiated requests** (`roots/list`,
   `sampling/createMessage`, `elicitation/create`): servers return an
   `InputRequiredResult` and the client retries with `inputResponses`.
8. **Every result carries a required `resultType`.**
9. **SSE resumability and message redelivery are removed**; a broken stream
   loses the in-flight request.

Plus minor-but-real: required `ttlMs` and `cacheScope` on all list results,
required `Mcp-Method` / `Mcp-Name` headers on Streamable HTTP POSTs, and the
resource-not-found error code moving from `-32002` to `-32602`.

## What a migration would have to decide

Not attempted here, and it needs the owner's call on scope:

- **Does `readwise-reader` need to move at all?** It is a local STDIO server for
  one user. The stateless redesign mostly buys things a single-user local server
  does not need. "Stay on 1.28.1 until the SDK drops 1.x support" is a
  defensible answer, and cheaper than migrating.
- **If it moves**, `server/discover` is mandatory, the handshake disappears, and
  every result needs `resultType`. The SDK does most of it, but the app's
  surface changes.
- **`skill-dashboard`** depends on `ext-apps`, whose own spec-tracking timeline
  is separate. Check `coderef/mcp/ext-apps` before assuming they move together.

## Sourcing

The spec is already observable: `coderef/mcp/modelcontextprotocol` is a tracked
clone, so `skill-maintain sources` records its HEAD and the provenance join can
bind a section to it by SHA the same way it binds `coderef/agentskills`.
Nothing in `best_practices.md` currently asserts an MCP *spec* fact — the one
MCP claim there (the scoped `mcp__plugin_<plugin>_<server>__<tool>` matcher) is
a Claude Code fact sourced from the hooks page — so no citation was added on
that basis. If MCP guidance is ever written into that file, cite the clone, not
the website.
