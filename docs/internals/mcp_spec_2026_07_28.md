# MCP spec 2026-07-28: what it breaks, and where this repo stands

Filed 2026-08-07 when the owner asked to "source and update mcp to the latest
spec". The answer to the second half is that **it is a migration, not a bump**,
so this records the gap rather than papering over it.

**Status: nothing migrated.** One footgun closed (below); the migration itself
is unscoped and unstarted. Rechecked 2026-09-21: the spec's state model is
unchanged since this was filed, and what moved is around it (below).

## What changed around the spec, as of 2026-09-21

- **Claude Code's client speaks the new revision by default.** Its v2 MCP
  runtime (TypeScript SDK 2.0) is the default in every session since v2.1.274.
  It asks **HTTP** servers whether they support 2026-07-28 and uses it where
  they do; **stdio** servers stay on the legacy `initialize` handshake unless
  `MCP_PROTOCOL_NEGOTIATION=auto`. A channel server that negotiates the new
  revision is not registered as a channel.
- **Python SDK**: 2.0.0 (2026-07-28), 2.1.x, and 2.2.0 (2026-09-07); the 1.x
  line gets only critical and security fixes, latest 1.30.0 (2026-09-05). 1.30.0
  also changes legacy behaviour: Streamable HTTP sessions idle for 30 minutes
  are closed by default (`session_idle_timeout=1800`), and the client gets
  `404 Session not found` and must `initialize` again (commit `92120b4b`).
- **ext-apps** 2.0.0 (2026-09-08) moves to TypeScript SDK 2.x. Its migration
  guide states the MCP Apps wire protocol did not change; the breaking changes
  are API-level (zod 4, handler context, error classes).
- **The Skills extension (SEP-2640) is Final.** Claude Code does not implement
  it, and plugin `skills/` already deliver the same format; revisit when Claude
  Code's MCP documentation lists it.

Claude Code probes HTTP servers for the new revision and not stdio ones, and
no remaining server here is HTTP: `mece-decomposer` runs over stdio and stays
on the legacy handshake by default. `readwise-reader`, the one HTTP server and
the one Python server, was retired on 2026-09-24 (changelog 1.66.0); the
section below records how it was pinned while it lived.

The current Python SDK is **2.0.0**, whose `LATEST_PROTOCOL_VERSION` is
`2026-07-28`. Note its `DEFAULT_NEGOTIATED_VERSION` is still `2025-03-26`, so
"the SDK supports the new spec" and "your server speaks it" are different
claims.

Derive the transport from each plugin's `.mcp.json`, the pins with `grep mcp
apps/*/pyproject.toml apps/*/mcp-app/package.json`, the installed versions from
the lock or `node_modules`; the third by reading
`coderef/mcp/modelcontextprotocol/docs/specification/2026-07-28/changelog.mdx`.

## The footgun that was live

`readwise-reader` is an application and floor-pinned `mcp[cli]>=1.26.0`. Since
`mcp` 2.0.0 is published, **any re-lock would have crossed a major boundary
silently** and pulled an SDK implementing a stateless protocol under code
written for a stateful one. The repo's own convention already says applications
pin exact; this one did not. Now `==1.28.1`, matching what its lock already
resolved.

`skill-dashboard` and `mece-decomposer` are the milder version of the same:
`^1.24.0` on an application, where the convention says exact. A caret cannot reach 2.x, so it is
a convention drift rather than a hazard. Left alone pending the same decision.

## Why 2026-07-28 is a migration

From the spec's own changelog. These are not additive:

1. **Protocol-level sessions removed** from Streamable HTTP, along with the
   `Mcp-Session-Id` header. Cross-call state becomes explicit server-minted
   handles passed as ordinary tool arguments.
2. **MCP is stateless**: the `initialize` / `notifications/initialized`
   handshake is gone. Every request carries its protocol version and client
   capabilities in `_meta`.
3. **`server/discover` is mandatory** — servers MUST implement it to advertise
   supported versions, capabilities, and identity.
4. **`subscriptions/listen` replaces** the HTTP GET endpoint and
   `resources/subscribe` / `resources/unsubscribe`.
5. **`ping`, `logging/setLevel`, and `notifications/roots/list_changed` are
   removed.** Log level moves to a per-request `_meta` field.
6. **Tasks leave the core protocol** for an `io.modelcontextprotocol/tasks`
   extension, with polling via `tasks/get` replacing blocking `tasks/result`.
7. **MRTR replaces server-initiated requests** (`roots/list`,
   `sampling/createMessage`, `elicitation/create`): servers return an
   `InputRequiredResult` and the client retries with `inputResponses`.
8. **Every result carries a required `resultType`.**
9. **SSE resumability and message redelivery are removed**; a broken stream
   loses the in-flight request.

Plus minor-but-real: required `ttlMs` and `cacheScope` on all list results,
required `Mcp-Method` / `Mcp-Name` headers on Streamable HTTP POSTs, and the
resource-not-found error code moving from `-32002` to `-32602`.

## What a migration would have to decide

Not attempted here, and it needs the owner's call on scope:

- **`readwise-reader`: settled by retirement** on 2026-09-24. Readwise now runs
  a hosted MCP server, and the successor builds on it outside this repo, so
  nothing here needs the Python SDK's 2.x migration.
- **`skill-dashboard` and `mece-decomposer`** depend on `ext-apps`, whose 2.0.0
  kept the wire protocol and changed the API; that is a code migration on the
  TypeScript side, separate from the spec's.

## Sourcing

The spec is observable: `coderef/mcp/modelcontextprotocol` is a tracked clone,
so `skill-maintain sources` records its HEAD and the provenance join binds a
section to it by SHA. Since 2026-09-21 `best_practices.md` carries the rules
this implies for authors (`MCP servers a plugin bundles`), cited to that clone
and to Claude Code's `mcp` page; this file keeps the repo's own standing.
